# 公众号排版与草稿回读验收

用于 Markdown 转换、排版修复和已有草稿更新。以下经验来自实际出现的名称加粗错位、文末样式丢失和草稿回读漏检；按当前文章及用户要求应用，不固定文章的引用条数、图片数量或重点词。

## 中文名称的加粗不能只看源文

中文引号、标点与连续 `**` 的组合可能让 Markdown 解析器把强调边界配错。已出现过 `**「名称甲」**和**「名称乙」**` 在成品中留下星号，反而把「和」加粗的情况。

先看生成后的可见文本和 `<strong>` 节点。出现该问题时，将相关名称改成显式内联 HTML，颜色沿用当前文章的强调色（以下为 SurviAGI 正文近黑）：

```html
<strong style="color: #202120; font-weight: 700;">「名称甲」</strong>和<strong style="color: #202120; font-weight: 700;">「名称乙」</strong>
```

验收完整名称是否在同一个 `strong` 中、颜色及字重是否生效、连接词是否仍为普通文字。扫描读者可见的正文是否残留 `**`；代码示例或文章主动讲解 Markdown 时按语境排除。不要用全局删除星号掩盖解析问题。

## 参考资料与落款需要独立样式

普通 Markdown 段落会套用正文样式；`*落款*` 只表示斜体，不表示小号灰字。人工维护的 `[1]` 参考段落也不会自动获得主题的脚注 class。`a`、`em` 等子元素自己的颜色可能覆盖父元素，所以要检查父子节点。

当前统一顺序：正文 → 品牌署名 → 参考资料。新稿的署名不使用 Markdown 斜体。文字及署名样式配置见 [signature.json](../assets/editorial/signature.json)；转换器在 CSS 内联之后应用 `article-endmatter.mjs`。这套规则仅处理新品牌署名及其参考区，历史文章保留原样。

| 区域 | 内联样式 |
|---|---|
| 署名区 | 上边距 32px、左右 8px；顶部 `1px solid #D4D3CE`；上内边距 16px；左对齐 |
| 来源署名文字 | 12px、1.8 倍行距、`#6E6F69`、正常字形；完整品牌名 600 字重；英文 IBM Plex Mono；自然换行 |
| 参考资料标题 | 14px、600 字重、`#6E6F69`；边距 `24px 8px 12px`；无装饰线 |
| 参考条目及链接 | 12px、1.8 倍行距、`#6E6F69`；条目边距 `6px 8px`；链接无下划线 |

项目默认署名保留一次：`本文由「新人类 AI 生存指南（SurviAGI）」完成信息监测、分析、选题与写作。` 放在参考资料前。完整中英文品牌名称保持加粗，不强制在品牌名后换行。完整句子与名称以`signature.json`为唯一文字配置源；此处是正文品牌称呼，不替换正式字标。历史落款由检查器兼容，当前用户要求优先。

若转换器的 CSS 内联处理覆盖了局部样式，在其输出之后，对明确的参考资料区域和落款做限定范围的后处理。不能把正文中的 `[1]` 引用句误当参考条目。保留引用编号、标题、链接与顺序，条数从文章实际内容计算。

将必要后处理写进文章的生成入口，使重跑能够保留修复。不要只改一次生成 HTML；也不要因一篇文章的版式要求修改所有文章共用的段落样式。本地预览与待上传 HTML 从同一份后处理结果生成，仅图片区分本地路径和微信 CDN URL。

## 更新与图片复用

### 公众号封面的两种画面

封面同时交付与目视检查 2.35:1 横版和 1:1 方形缩略图。两版都保留用户确认的标题和可识别的主体，并检查 200px、96px 方图；需要不同版式时分别排版，不能用裁掉标题的机器特写充当方图。

API 的两个裁切字段都基于同一个永久素材。可在同一上传母版安排两个独立版式区域，再分别配置裁切。回读 `cover_info.crop_percent_list`，核对实际坐标、比例和完整内容。展示给用户的是两种裁切后的画面，母版另存。

`draft/get` 的 `thumb_url` 可能已经是横版裁切图；永久素材上传响应的 `url` 才是原始母版。分别下载核对，不要在已裁切的 `thumb_url` 上再次套用母版坐标。更新时保留当前正文；将返回 HTML 再次写入前，仅在 style 属性中解码 `&#39;` 等已确认会导致平台丢样式的转义，并以文本、结构和 CSS 语义回读验收。

1. 读取现有草稿，保留快照并比较上次回读，发现后台手改时先合并。沿用记录中的 `media_id` 和文章位置；避免修样式时新增重复草稿。
2. 转换本次 Markdown。已有一套人工编号参考资料时使用 `--no-cite`；保留手工插入的媒体，执行限定范围的排版后处理。
3. 根据本次转换的 `images[]` 核对图片。图片内容相同才可复用已有 CDN URL；顺序变化时重新生成占位符对应关系，不能直接沿用旧编号。仍有 `WECHATIMG_N` 时运行 `replace-images.mjs`，即使没有新图片上传。
4. 保留标题、作者、摘要、原文链接、封面 ID、评论配置等字段。封面裁切及手工媒体也要在更新后核对；不要把读取响应里的 URL 等只读字段不加区分地传回更新接口。
5. 调用更新后重新 `draft_get`，核验本次内容。HTTP 成功或 `errcode:0` 仅证明接口接受操作。

## 三层验收

| 层次 | 验收内容 | 不能代替什么 |
|---|---|---|
| Markdown | 文案、引用、图片存在、文风和项目落款规则 | 不能证明加粗和字号已正确渲染 |
| 最终 HTML 与预览 | 可见文本、完整重点词、内联字号颜色、文末层级；可用时目视检查 | 本地正确不能证明草稿已经同步 |
| 本次远端回读 | 正文、语义样式、图片资源、元数据和媒体保留 | HTML 字段正确不等于手机端目视验收 |

**正文一致只是其中一项。** 错误 HTML 上传后再逐字回读，仍然可能完全一致。应根据用户要求与文章内容独立验证：

- 重点名称完整处于强调节点，检查字重与颜色；连接词不误加粗，可见正文无意外 Markdown 标记。
- 参考标题、每条参考资料及链接、落款及其子元素的最终字号颜色符合当前版式；编号及落款次数正确。
- 正文没有未替换占位符或本地文件路径。状态句按真实完整表述核验，不能因为检查脚本预设了别的措辞而改写已经确认的文案。
- 正文图片数量和顺序与本次文章对应。微信可能将 `src` 改为 `data-src`、HTTP 改 HTTPS、图片末尾 `/0` 改为 `/640`。允许已观察到的尺寸变换后，仍比较域名、完整资源 ID 与 alt；不能只比较张数或忽略整个路径。
- 标题、作者、摘要、原文链接、封面 ID 与裁切、评论开关、文章位置、手工媒体按预期保留。

解析 HTML 或使用 DOM 检查语义，不比较整串 HTML 字节；微信可改变属性顺序或 URL 形式。颜色等价写法也应按实际语义判断。记录每项结果，不沿用旧的“全部通过”。

浏览器阻止本地文件访问时，遵守拒绝边界。仍可检查文件内容及通过既有授权接口回读草稿，但应注明目视复查未完成，不尝试用其他地址或工具绕过被拒绝的访问。

## 服务回退与交付记录

MCP 工具不可见时，可用已有 `WECHAT_API_KEY` 访问 `WECHAT_API_BASE_URL` 指定的同一服务，默认地址见主 skill。不要因此推断服务宕机或要求用户重新部署。

- JSON 请求体使用结构化参数或 UTF-8 JSON 文件；长正文不要拼进 shell 命令。密钥只经环境和请求头传递，避免写进参数日志、响应记录或文章文件；使用 curl 时可通过 stdin config 注入认证头。
- 同时检查传输状态和响应体 `errcode`。写入超时或结果不明确时先查询状态，不盲目重试创建/更新；读取失败可有界重试。
- 文章目录保留生成入口、转换清单、图片映射、更新前快照、写入响应、本次回读及验收结论。身份凭据不落盘，临时预览链接按需保留在本地交付记录。
- 文风扫描可能把 HTML 属性的英文双引号误报成文案问题。定位后保留合法标记；仍检查正文，不因进程退出码为 0 就称文风通过。例外及检查限制写在交付记录，不塞入文章正文。

向用户说明本地是否已更新、远端原草稿是否已更新以及实际完成的验证范围。草稿保存不等于正式发表。
